# ワーキングメモリに依存しない改善バックログ

仕事上の改善点は、覚えて意識し続けるのではなく、必要な場面で自動的に実行される仕組みに変える。改善案の合格条件は、**改善点を完全に忘れていても、必要な行動が実行されるか、確認しないと次へ進めないこと**とする。

## 改善策の優先順位

上にある対策ほど、ワーキングメモリへの依存が少ない。

| 優先度 | 対策 | 例 | 忘れていても機能するか |
| --- | --- | --- | --- |
| 1 | 自動化する | 機械的な表記確認を自動チェックする | 機能する |
| 2 | 実行しないと進めないゲートにする | 納品前チェックが未完了なら納品完了にしない | 機能する |
| 3 | テンプレートや初期値に埋め込む | 質問文を決まった入力欄から作成する | ほぼ機能する |
| 4 | 必要な瞬間に通知する | 納品予定時刻の前に確認タスクを通知する | 通知に気づけば機能する |
| 5 | 作業場所に注意書きを置く | 納品フォルダーに確認事項を表示する | 見落とす可能性がある |
| 6 | 意識する、気をつける | 次回から注意すると決める | 機能しにくい |

改善策を考えたら、まず自動化できないか検討する。難しい場合は、ゲート、テンプレート、通知の順に落とし込む。「意識する」「注意する」だけの改善案は完了扱いにしない。

## 改善バックログの流れ

```text
ミスや指摘が発生する
        ↓
改善候補をバックログへ記録する
        ↓
どの操作・工程で発生したか特定する
        ↓
その工程に自動化・ゲート・テンプレートなどを埋め込む
        ↓
改善点を忘れた状態でも機能するか確認する
        ↓
機能すれば完了、機能しなければ仕組みを修正する
```

バックログを作るだけでは放置される可能性がある。バックログを処理する予定もカレンダーに定期登録し、一度に仕組み化する項目は1件に制限する。

## 最小限の管理項目

記載コストを下げるため、発生時には「改善候補」だけを登録する。詳しい情報は、実際に仕組み化するときに追記する。

| 項目 | 登録する時期 | 内容 |
| --- | --- | --- |
| 改善候補 | 発生時 | 何が起きたかを一文で書く |
| 状態 | 自動または選択 | バックログ、仕組み化中、確認中、完了 |
| 発動条件 | 仕組み化するとき | どの瞬間に対策が必要になるか |
| 仕組み | 仕組み化するとき | 自動化、ゲート、テンプレート、通知など |
| 完了条件 | 仕組み化するとき | 忘れていても機能したと判断できる条件 |
| 完了日 | 完了時 | 消化数と所要日数の集計に使う |

分類、原因、重要度などを最初から必須にすると登録しなくなるため、必要になるまで増やさない。

## 具体例

### 質問の仕方

| 項目 | 内容 |
| --- | --- |
| 改善候補 | 前提を共有せず、抽象的な質問をした |
| 発動条件 | 誰かへ判断を求めるメッセージを作成するとき |
| 仕組み | 背景、確認済みの事実、自分の理解、不明点、自分の案、質問を含むテンプレートから作成する |
| 完了条件 | 相手が追加の前提確認をせず、可否や選択肢を回答できる |

### 納品前のケアレスミス

| 項目 | 内容 |
| --- | --- |
| 改善候補 | 納品物の表記や添付を確認せず提出した |
| 発動条件 | 納品タスクを完了にするとき |
| 仕組み | 内容確認、表記確認、納品物確認を子タスクにし、すべて完了するまで納品完了にしない |
| 完了条件 | 確認項目の完了記録があり、実際の納品物を開いて確認している |

### 過去のレビュー指摘

レビュー指摘は、そのまま「次は注意する」と記録せず、発生した条件と確認方法へ変換する。

| 指摘 | 発生条件 | 仕組みに変換した確認 |
| --- | --- | --- |
| 用語の修正漏れ | 用語を変更した | 変更前の用語を全体検索する |
| 条件分岐の考慮漏れ | 表示条件を追加した | 条件の組み合わせを列挙する |
| レビュー前に提出した | レビュー工程が複数あった | レビュー完了と提出許可がそろうまで提出不可にする |

## 確認する指標

グラフを増やすこと自体を目的にせず、仕組みが回っているか判断できるものだけを確認する。

| 指標 | 分かること |
| --- | --- |
| 月ごとの仕組み化完了数 | バックログが実際に処理されているか |
| 登録から完了までの日数 | 改善候補が長期間放置されていないか |
| 対策方法の内訳 | 「意識する」ではなく、自動化やゲートへ移せているか |
| 同種ミスの再発数 | 作った仕組みが実際に機能しているか |

最初に作るグラフは「月ごとの仕組み化完了数」だけでよい。記録が蓄積してから、必要な指標を追加する。

## 管理サービスの比較

2026年9月15日時点の公式情報を基に比較する。

| サービス | 無料利用とグラフ | 記載コスト | 向いている使い方 | 判断 |
| --- | --- | --- | --- | --- |
| Notion | 無料プランでデータベース、基本フォーム、グラフ1つを利用できる | 低い | バックログ管理と月別完了数の確認を一か所で始める | 最初の候補 |
| Googleフォーム＋スプレッドシート | フォーム回答をシートへ保存し、ピボットテーブルや複数のグラフで分析できる | 登録は非常に低い。管理画面の作成はやや必要 | 無料で複数の集計やグラフを作りたい | グラフ重視の候補 |
| GitHub Projects | GitHub FreeにIssuesとProjectsが含まれ、ProjectsのInsightsで現在値と履歴のグラフを作成できる | 中程度 | GitHub上の作業と改善バックログをまとめる | GitHubを毎日使う場合の候補 |
| Redmine | ソフトウェア自体はGPL v2のオープンソース。標準機能にチケット、ガント、カレンダー、時間レポートがある | 高い | サーバーを用意し、複数プロジェクトや細かなワークフローを管理する | 個人の改善管理には重い |

### Notion

Notionでは、データベースを表、リスト、ボード、カレンダー、グラフなどで表示できる。無料プランでも利用できるが、作成できるデータベースグラフは1つで、有料プランでは無制限になる。そのため、最初は「月ごとの仕組み化完了数」を1つだけ表示する運用に向いている。

登録用のビューでは改善候補だけを入力し、発動条件や完了条件は「仕組み化中」に移した後で入力する。これにより、発生時の記載コストを抑えられる。

### Googleフォーム＋スプレッドシート

Googleフォームの回答は自動的にGoogleスプレッドシートへ保存でき、フォーム側の回答グラフに加えて、スプレッドシートでピボットテーブルやグラフを作成できる。登録はフォームから「改善候補」を送信するだけにできる。

一方、バックログの状態変更や並べ替えはNotionより扱いにくい。複数グラフを無料で作ることを優先する場合に向いている。

### GitHub Projects

GitHub FreeにはIssuesとProjectsが含まれている。ProjectsのInsightsでは、プロジェクト内の項目を基に、フィルター、グラフ形式、表示項目を設定した現在値と履歴のグラフを作成できる。

すでにGitHubを毎日開くなら管理場所を増やさずに済む。ただし、仕事中の小さな気づきを素早く登録する用途では、NotionのフォームやGoogleフォームより入力が重くなりやすい。

### Redmine

Redmine本体はオープンソースなので、自己管理する環境へインストールすればライセンス料金なしで個人利用できる。ただし、公式の導入手順にはRuby、データベース、依存関係、設定、バックアップなどが含まれる。クラウド上のRedmineサービスが無料になるという意味ではない。

標準機能は柔軟なチケット管理、ガントチャート、カレンダー、時間レポートなどが中心である。個人の改善バックログと消化数のグラフだけが目的なら、導入と保守の負担が大きい。

## 現時点のおすすめ

まずはNotionの無料プランで開始する。

1. 改善候補だけをすぐ登録できるデータベースまたはフォームを作る。
2. 状態を「バックログ、仕組み化中、確認中、完了」の4つにする。
3. 月ごとの仕組み化完了数を、無料枠の1グラフとして表示する。
4. 毎週1回、バックログから1件だけ選び、仕組み化する予定をカレンダーへ登録する。
5. 1つのグラフでは判断できなくなった段階で、GoogleスプレッドシートまたはGitHub Projectsへの移行を検討する。

複数グラフが最初から必須なら、Googleフォーム＋スプレッドシートを選ぶ。Redmineは、チケット管理そのものを学びたい、または自分でサーバーを管理したい場合を除き、今回の目的では選ばない。
