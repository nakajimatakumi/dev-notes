# React・Vueの新規開発における技術選定事例

ReactまたはVueを新規開発で採用した公開事例から、実際に挙げられていた選定理由を整理する。

ここで扱うのは、単純な機能比較や「どちらが優れているか」ではない。新しいプロダクト、画面、アプリケーションを作る際に、案件の要件やチーム事情がどのような判断につながったかを確認する。

## 調査対象と読み方

事例は、次の3種類に分けて扱う。

| 情報の種類 | 読み取り方 |
| --- | --- |
| 公開ADR | 比較候補、判断基準、決定結果が明示されており、選定理由の根拠として比較的強い |
| 企業・プロダクトの技術ブログ | 実際の開発背景を確認できるが、採用技術を肯定的に説明する立場から書かれている |
| 担当者の投稿・インタビュー | 現場の具体的な判断を確認できるが、組織全体の正式な評価や網羅的な比較とは限らない |

「新規開発」には、完全なGreenfieldだけでなく、既存組織内で新しいアプリや新しいモジュールを作った事例も含める。ただし、既存技術からの置き換えが判断へ強く影響している事例は、その点を明記する。

また、過去の選定理由は当時のバージョン、エコシステム、チーム構成を前提としている。現在の一般的なReactとVueの優劣を、そのまま証明するものではない。

## React・Next.jsを選んだ事例

### Simpler.Grants.gov

- **プロジェクトと新規開発の背景**：政府助成金サービスの新しいフロントエンドで、サーバー側で最新情報を表示するページと、検索や絞り込みなどクライアント側で操作するページの両方が必要だった。
- **比較された候補**：Create React App、Next.js、VueまたはNuxt、SvelteまたはSvelteKit。
- **選択された技術**：Next.js。
- **実際に挙げられた選定理由**：SSRとCSRを含む技術要件を満たすこと、大きなコミュニティ、学びやすさと文書、開発を担当するNavaのチームが理解していること。認証・認可、国際化、ミドルウェアも評価項目に含まれていた。
- **その理由から読み取れる判断基準**：新規サービスではReactとVueのコア機能だけでなく、Next.jsやNuxtを含めて、レンダリング方式、認証、ルーティング、国際化などのアプリケーション要件を比較する必要がある。チームがすでに安全に運用できることも独立した判断材料になる。
- **情報の注意点**：React単体ではなくNext.jsを選んだ事例である。公開ADRは2023年7月14日付で、当時の技術とチーム状況に基づく。

### COREbeat

- **プロジェクトと新規開発の背景**：COREbeatのWebアプリケーションで使用するフロントエンド技術を選定した。
- **比較された候補**：React、Angular、Vue。
- **選択された技術**：React。
- **実際に挙げられた選定理由**：ドキュメント、コミュニティの支援、サードパーティーツール、幅広いライブラリ。Angularのように機能を一括して持つ構成ではなく、必要なツールを選べる自由も理由としている。
- **その理由から読み取れる判断基準**：エコシステムは利用者数の大小だけでなく、今回必要なライブラリと問題解決の情報が存在するかで確認する。周辺構成をチームで選択できるなら、Reactの選択肢の多さを利点にできる。
- **情報の注意点**：記事中の「Reactは大規模向け」「Vueの支援はReactより少ない」という評価は同社の判断であり、一般的な事実として扱わない。記事は2022年11月14日公開。

### JITR

- **プロジェクトと新規開発の背景**：高速な初期表示、テナント間の画面遷移、管理画面から多数の機能モジュールまで拡張できる構成を必要とするマルチテナントSaaSの新規フロントエンド。
- **比較された候補**：記事では複数案を評価したと説明しているが、候補ごとの詳細な比較表は公開されていない。
- **選択された技術**：React 19、Vite 6、Tailwind CSS v4。
- **実際に挙げられた選定理由**：Suspense、`use()`、Transition、通常のPropsとして扱える`ref`など、非同期表示やコンポーネント設計へ直接関係するReact 19の機能。Viteによる開発時のフィードバック速度と、React向け管理画面UI基盤も構成全体の理由になっている。
- **その理由から読み取れる判断基準**：バージョン固有の機能を理由にする場合は、「新しいから」ではなく、ローディング、画面遷移、権限変更など対象プロダクトの具体的な操作へ結び付ける。すでに利用できるUI基盤も実装コストを左右する。
- **情報の注意点**：2026年1月12日公開の自社記事であり、第三者による比較評価ではない。ReactとVueを一対一で比較した事例でもない。

### Green13

- **プロジェクトと新規開発の背景**：保険数理モデルを作るための、応答性が高くデータ駆動型のブラウザーUIと新しいツール群を開発した。
- **比較された候補**：記事ではAngularJSから離れてReactを選んだ理由を説明している。Vueとの直接比較ではない。
- **選択された技術**：React。
- **実際に挙げられた選定理由**：JSXでロジックとマークアップを近くに置けること、単方向データフローの透明性と予測可能性、View層として周辺技術を選べる柔軟性、コミュニティ、ピッカー・グラフ・ボタンなどの既存部品。
- **その理由から読み取れる判断基準**：分岐やデータ変換が多いUIでは、JavaScriptとマークアップを一緒に扱う方がチームの思考に合うかを確認する。自由にライブラリを選ぶ価値と、選定・統一を担当する人が必要になるコストを対で評価する。
- **情報の注意点**：旧AngularJS構成から新しいツール群を作った事例であり、完全に既存技術の影響がないGreenfieldではない。中心開発者による2019年5月13日の投稿である。

### Omnia

- **プロジェクトと新規開発の背景**：既存のReact Webアプリを継続開発しながら、新しくiOS・Androidアプリを作る必要があった。エンジニアリング組織を大幅に増員しない方針だった。
- **比較された候補**：React Native、Flutter、プラットフォーム別のネイティブ開発。
- **選択された技術**：React Native。
- **実際に挙げられた選定理由**：Reactのメンタルモデルを引き継げること、Webと同じAPIやサービス基盤を利用できること、開発エコシステムが成熟していたこと、少人数のフルスタックチームが複数クライアントを横断して担当できること。
- **その理由から読み取れる判断基準**：将来モバイルアプリを作る計画が具体的なら、コードの完全共有ではなく、言語、設計知識、API利用方法、担当者の移動可能性を含めてReact Nativeとの連続性を評価する。
- **情報の注意点**：ReactとVueのWeb開発を直接比較した事例ではなく、将来のモバイル展開がReact選定へ影響し得ることを示す補足事例である。記事は2022年4月25日公開。

## Vue・Nuxtを選んだ事例

### Crossref

- **プロジェクトと新規開発の背景**：Greenfieldのユーザーインターフェースを作るため、新しいフロントエンド構成を選べる状況だった。
- **比較された候補**：Vue、Angular、Svelte、React。
- **選択された技術**：Vue。
- **実際に挙げられた選定理由**：再利用可能なコンポーネント、堅牢なリアクティビティ、安定した学習曲線、良いドキュメント、活発なコミュニティ。新しい開発者が習得しやすく、Crossrefの利用者である研究者にもVue利用者がいたことを肯定的な結果としている。
- **その理由から読み取れる判断基準**：開発チームだけでなく、プラグインや画面を作る可能性がある利用者層の技術経験も選定材料になる。学習しやすさは抽象的に評価せず、参加予定者が試作を理解・変更できるかで確認する。
- **情報の注意点**：2020年7月20日に承認された公開ADRである。既存のReactアプリを拡張しないことも不利益として記録されており、Vueだけを肯定した資料ではない。

### Magic as a Service

- **プロジェクトと新規開発の背景**：デザインとエンジニアリングを横断する小規模チームが、複数の商用プロジェクトを継続して開発している。
- **比較された候補**：記事では当時の主要な候補を試したと説明しているが、個別の比較結果は示していない。
- **選択された技術**：VueとNuxt。
- **実際に挙げられた選定理由**：他の構成がチームには不要または理解し切れない複雑性を加えていたこと、Vueの考え方がチームに合ったこと、NuxtがルーティングやSSRを含む意見のある構成を提供し、繰り返し発生する設計上の議論を減らせたこと。
- **その理由から読み取れる判断基準**：少人数チームでは、選択肢の多さより、全員が理解できる構成と意思決定の少なさが開発速度へ影響する。フレームワークの機能だけでなく、チームが独自の設計規約を作り続ける余力を評価する。
- **情報の注意点**：2025年7月13日の回顧記事であり、導入当時の比較資料ではない。同社はVue/Nuxt向けの社内ツールキットを持つため、現在の継続判断には既存資産も影響している。

### Superthread

- **プロジェクトと新規開発の背景**：ゲームのように即時に反応し、細部まで快適に操作できることを目標とした新規SaaSプロダクト。
- **比較された候補**：React、Angular、Vue。
- **選択された技術**：Vue。
- **実際に挙げられた選定理由**：軽量、応答が速い、使いやすい、柔軟で、高性能なインターフェースを作れるという開発者の評価。
- **その理由から読み取れる判断基準**：操作速度が重要なら、目標となるユーザー操作と応答時間を先に定義し、候補技術で試作して計測する。フレームワーク名だけで性能を決めない。
- **情報の注意点**：2021年1月23日に創業者が公開した説明である。「17ミリ秒」はプロダクトの目標であり、ReactとVueを同条件で測った比較ベンチマークではない。APIの4ミリ秒という記載もローカル環境でバックエンドを測った値で、Vueのレンダリング性能を示す値ではない。

### Inkleaf

- **プロジェクトと新規開発の背景**：図書館の業務をまとめて扱う新しいプラットフォームを開発した。
- **比較された候補**：インタビューでは、より普及している候補としてReactへ言及している。
- **選択された技術**：Vue。
- **実際に挙げられた選定理由**：VueのシンプルさとSingle File Componentのモデル。
- **その理由から読み取れる判断基準**：テンプレート、処理、スタイルをSFC単位で把握する方法が、チームのレビューや保守の仕方に合うかを確認する。
- **情報の注意点**：2024年10月15日掲載の創業者インタビューで、候補の評価表や試作結果は公開されていない。選定理由の技術的な深さより、作り手が重視した価値観を示す事例として扱う。

### SPHEREboard

- **プロジェクトと新規開発の背景**：複雑で重複したUIを改善し、新しいページやモジュールを作るためのフロントエンド構成を検討した。
- **比較された候補**：React、Vue。
- **選択された技術**：VueとVuetify。
- **実際に挙げられた選定理由**：Vueを始めやすいこと、システムの成長に応じて高水準の機能を追加できるエコシステム。Vuetifyは成熟度、支援状況、画面を短時間で形にできることを理由に選んだ。
- **その理由から読み取れる判断基準**：フレームワークだけでなく、採用するUIコンポーネントライブラリまで組み合わせて、必要な画面をどの程度早く一貫して作れるかを評価する。
- **情報の注意点**：既存製品内で新しいページやSPAモジュールを作った事例で、完全なGreenfieldではない。記事は2024年5月17日公開。

### Optoro

- **プロジェクトと新規開発の背景**：既存組織の複数チームが新しいアプリを計画する中で、AngularJSの次に使うフロントエンド技術を選定した。
- **比較された候補**：React、Angular、Vue。
- **選択された技術**：Vue。
- **実際に挙げられた選定理由**：開発者が短期間で採用でき、大きな思考方法の変更を必要としないこと。AngularJS経験者にとってテンプレート、ディレクティブ、コンポーネントが親しみやすいこと、文書とコミュニティへの信頼、npm scriptsを通して既存ビルド環境へ組み込めること。
- **その理由から読み取れる判断基準**：学習コストは一般的な難易度ではなく、チームが現在知っている構文や設計との距離で決まる。ビルド、テスト、Lintを既存の開発フローへ組み込めるかも選定対象になる。
- **情報の注意点**：新しく作るアプリへVueを採用した一方、判断にはAngularJS中心だった組織の経験が強く影響している。純粋なGreenfield事例ではなく、記事は2019年5月17日公開。

## 事例から抽出できる判断基準

### 1. 周辺技術を選ぶ自由と、その判断を維持する能力

Green13やCOREbeatでは、必要なツールを選べるReactの柔軟性が利点になっている。一方、Magic as a Serviceでは、Nuxtが代表的な構成を提供し、設計上の議論を減らせることが利点になっている。

これは「自由なReact、制約のあるVue」という単純な差ではない。次を判断する。

- ルーティング、データ取得、状態管理、フォームなどをチームで選定・更新できるか。
- 選択肢を増やすことで、プロダクト固有の要件を満たしやすくなるか。
- 標準構成へ寄せることで、実装方法のばらつきや議論を減らせるか。

### 2. UIを理解する際の中心をどこに置くか

Green13では、複雑なデータと表示ロジックをJSXで近くに置けることがReactの理由になった。Inkleafでは、VueのSFCモデルが理由になった。

- 条件分岐やデータ変換をJavaScriptやTypeScriptの処理として追いたいか。
- テンプレート、処理、スタイルを明確な領域に分けて読みたいか。
- デザイナー、バックエンド開発者なども含め、誰がコンポーネントを読むか。

どちらでも複雑なUIは作れるため、実現可能性ではなく、チームが安全に理解・レビューできる表現を比較する。

### 3. 必要なUI部品と既存資産

Green13はグラフなどのReactコンポーネント、SPHEREboardはVuetify、JITRはReact向け管理画面基盤を理由に含めている。抽象的なエコシステムの大きさより、必要な資産を具体的に列挙して確認する。

- データグリッド、グラフ、エディター、フォームなどの必要部品。
- アクセシビリティやデザイン要件を満たすUIライブラリ。
- 社内のデザインシステム、コンポーネント、開発テンプレート。
- 認証、監視、テストなど周辺サービスとの統合。

### 4. Next.js・Nuxtまで含めたアプリケーション要件

Simpler.Grants.govやMagic as a Serviceでは、ReactとVue単体よりもNext.jsやNuxtが提供する構成が判断へ影響している。

- SSR、SSG、CSRをどのページで使うか。
- ルーティング、認証・認可、国際化、ミドルウェアが必要か。
- サーバー側処理、キャッシュ、デプロイ先に制約があるか。
- チームが運用方法まで理解しているか。

### 5. チームの経験から習得までの距離

Crossrefでは研究者を含む利用者層、OptoroではAngularJS経験者、Simpler.Grants.govでは担当チームの既存知識が判断材料になった。

「Vueは初心者向け」「Reactは経験者向け」と一般化せず、候補ごとに同じ試作を変更してもらい、必要な教育時間とレビュー負荷を確認する。

### 6. チーム規模と役割分担

OmniaはWebとモバイルを横断する少人数チーム、Magic as a Serviceはデザインとエンジニアリングを横断する小規模チームに合うことを理由としている。

- 専任のフロントエンド基盤担当者がいるか。
- 少人数でWeb、サーバー、モバイルを横断するか。
- 新しいライブラリの評価や更新を誰が担当するか。
- 採用後に人数やチーム数が増えた場合、規約を共有できるか。

### 7. モバイルなどWeb以外への展開

Omniaの事例では、React NativeによってReactの考え方とAPI利用方法を共有できることが、少人数体制に合っていた。

将来のモバイル展開が単なる可能性ではなくロードマップに含まれる場合は、React Nativeの採用可能性をReact側の判断材料にできる。ただし、DOM向けコンポーネントがそのままネイティブUIになるわけではないため、共有できる範囲を試作で確認する。

### 8. 性能は対象操作で検証する

Superthreadは高速な操作感をVueの理由に挙げ、JITRは非同期UIに関係するReact 19の機能を理由に挙げている。ただし、これらはReactとVueを同条件で比較した性能データではない。

- 初回表示、画面遷移、フォーム入力、大量一覧など、重要な操作を定義する。
- 同じデータ量、端末、ネットワーク、レンダリング方式で試作する。
- フレームワークの処理だけでなく、JavaScript量、API、画像、キャッシュも測る。
- 主観的な「軽い」「速い」と実測値を区別する。

### 9. AI・デザインツールとの親和性

今回確認した事例では、AIコード生成やデザインツール連携をReact対Vueの主要な決定理由として正式に記録したものは少なかった。そのため、現時点では一般論ではなく、チームが実際に使うツールで評価する項目とする。

- Figmaなどから利用するデザインシステムの実装が、どちら向けに提供されているか。
- AIへ同じ画面の実装・修正・テストを依頼し、正確さと修正コストに差があるか。
- 社内コードや設計規約を与えたとき、採用予定の構成へ一貫して従えるか。
- 生成されたコードをチームが理解してレビューできるか。

## 技術選定でそのまま使える確認項目

| 確認項目 | 確認方法 |
| --- | --- |
| プロダクト固有のUI | 最も複雑なフォーム、一覧、権限分岐を小さく試作する |
| 必要な部品 | データグリッド、グラフ、エディターなどを名前付きで列挙し、保守状況も確認する |
| フルスタック構成 | Next.jsとNuxtを含め、SSR、認証、国際化、キャッシュ、デプロイを比較する |
| 状態と更新経路 | 初見のメンバーが状態の所有者、派生値、副作用を説明できるか確認する |
| TypeScript | Props、イベント、フォーム、共通コンポーネントで型エラーとIDE補完を比較する |
| テスト | 同じユーザー操作のコンポーネントテストとE2Eテストを作る |
| チームの習得 | 説明を受けていないメンバーに試作の変更とレビューを依頼する |
| 設計判断の負担 | 採用時に決めるライブラリと規約、その維持担当者を列挙する |
| 性能 | 重要操作について目標値を定め、同じ条件で計測する |
| Web以外への展開 | React Nativeなどで共有できる知識、ロジック、UI、テストの範囲を確認する |
| AI・デザインツール | 実際のツールへ同じ課題を与え、生成品質、修正量、レビュー可能性を比較する |
| 長期保守 | 更新頻度、破壊的変更、依存ライブラリ、障害調査方法を確認する |

技術選定の結論は、次のように要件と理由を対応させて記録する。

> この案件では○○が必要であり、チームには△△という制約がある。試作では□□を満たしたため、ReactまたはVueを選択する。一方、××は採用後の負担として受け入れる。

「Reactは大規模向け」「Vueは初心者向け」「どちらかが常に高速」といった分類だけでは、案件固有の判断理由にならない。
