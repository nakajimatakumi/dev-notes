# ReactとVueの状態更新時の差分

ReactとVueは、どちらも状態から画面を宣言的に構築する。しかし、状態更新時に読み込み直す範囲と、状態の保持・変更を検知する方法が異なる。

このページでは、次の3つの差分について、違いが生まれる理由と双方のメリット・デメリットをまとめる。

1. 状態更新時に読み込み直す範囲
2. 状態の扱いと更新方法
3. 状態を作る場所と所有者

前提として、このページのReactは、React Compilerを有効にしていない関数コンポーネントの基本動作を基準とする。React CompilerはReact 18に標準搭載されておらず、別途導入するとコンポーネントや値のメモ化の多くをビルド時に自動化できる。

## 差分1：状態更新時に読み込み直す範囲

### 違い

| React                                             | Vue                                                                    |
| ------------------------------------------------- | ---------------------------------------------------------------------- |
| 状態を更新すると、対象の関数コンポーネントを再び呼び出し、コンポーネント本体を上から実行する | リアクティブな状態を更新すると、その値に依存するレンダー処理を実行する。`setup()`や`<script setup>`全体は実行し直さない |

### Reactの動作

Reactでは、再レンダー時に関数コンポーネントの本体を再実行する。

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  const formattedCount = `${count}回`;

  function increment() {
    setCount((current) => current + 1);
  }

  return <button onClick={increment}>{formattedCount}</button>;
}
```

`count`を更新すると、`Counter()`がもう一度呼び出される。その結果、次の処理が行われる。

- `formattedCount`を新しい`count`から再計算する。
- `increment`の新しい関数オブジェクトを作る。
- JSXを再計算する。
- 前回の結果と比較し、必要なDOMだけ更新する。

再レンダーは、画面のDOMをすべて作り直すことではない。コンポーネント関数を再実行して新しいUIを計算し、差分があるDOMだけを変更する処理である。

親コンポーネントが再レンダーされると、原則としてその子コンポーネントも再レンダーされる。子のPropsが同じでも、`memo`やReact Compilerなどで省略しない限り、子の関数も呼び出される。

### Vueの動作

Vueでは、`<script setup>`はコンポーネントインスタンスを作るときに実行される。

```vue
<script setup lang="ts">
import { ref } from "vue";

const count = ref(0);

function increment() {
  count.value++;
}
</script>

<template>
  <button @click="increment">{{ count }}回</button>
</template>
```

`count`が変わると、`count`を使用しているレンダー処理が実行され、テンプレートの表示が更新される。ただし、`count`や`increment`を定義している`<script setup>`全体は実行し直されない。

そのため、`<script setup>`で作った普通の変数は、元の`ref`が変化しても自動的には再計算されない。

```ts
const count = ref(0);
const formattedCount = `${count.value}回`;
```

`count.value`が`1`になっても、`formattedCount`は初期化時の`"0回"`のままである。テンプレートに`count`と`formattedCount`の両方を表示しても、この関係は変わらない。

追従する派生値にするには、`computed`を使う。

```ts
const formattedCount = computed(() => `${count.value}回`);
```

また、テンプレート内の式や、テンプレートから呼び出したメソッドは、レンダー処理が実行されると再評価される。

```vue
<template>
  <p>{{ count * 2 }}</p>
  <p>{{ formatCount() }}</p>
</template>
```

この場合、`formatCount`という関数自体を作り直すわけではないが、レンダー処理から`formatCount()`は再び呼び出される。

親が更新された場合も、子のPropsに変化がなければ子の更新を省略できる。Propsが変化した子ではレンダー処理を実行するが、子の`<script setup>`全体は実行し直さない。

### なぜ違うのか

| Reactの思想                               | Vueの思想                                   |
| -------------------------------------- | ---------------------------------------- |
| 状態とUIの関係を明示し、画面更新の原因がブラックボックスになることを避ける | 状態変更を直感的に画面へ反映し、依存関係や更新範囲を開発者が管理する負担を減らす |

#### React：画面更新の原因をコードから追いやすくする

Reactは、大規模な画面で「どのデータから、なぜこのUIが作られたのか分からなくなる」という複雑性を減らそうとしている。

そのため、Propsや状態を入力としてコンポーネントを実行し、UIを出力するという明示的な関係を重視する。入力が変わったら同じ関数を再実行する形にすることで、表示の原因をProps、状態、コンポーネントの処理から追いやすくしている。

依存関係を暗黙的に管理しない代わりに、不要な再計算を減らしたい場合は、状態の配置やメモ化などを開発者が検討する。

#### Vue：開発者が更新範囲を管理する負担を減らす

Vueは、「値を変更したら、それを使っている表示も更新される」という直感的な開発体験を重視している。

そのため、リアクティブな値と処理の依存関係をVueが記録し、値が変わったときの通知やテンプレートの最適化をフレームワーク側で行う。開発者が更新対象や再計算の範囲を細かく指定する必要を減らすため、コンポーネントを一度初期化し、依存関係を使って画面を更新する設計になっている。

つまり、Reactは「状態とUIの関係を明示する」ことで複雑性を減らし、Vueは「依存追跡と最適化をフレームワークが引き受ける」ことで複雑性を減らしている。

### メリット・デメリット

|       | メリット                                                                           | デメリット                                                                                  |
| ----- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| React | 通常のJavaScript関数として処理を追いやすい。単純な派生値は普通の変数として書くだけで状態へ追従する。レンダーを独立した純粋な計算として扱える | コンポーネント本体の計算、関数、オブジェクトを再生成する。上位の状態更新が広い子ツリーの再レンダーにつながることがあり、必要に応じて状態の配置やメモ化を検討する |
| Vue   | 初期化処理や関数定義を更新のたびに作り直さず、依存するレンダー処理へ更新を絞りやすい。`computed`は依存値が変わるまで結果をキャッシュできる     | 普通の変数は`ref`へ自動追従しない。`ref`、Proxy、`computed`、テンプレートの再評価範囲を理解しないと、更新される値と更新されない値を誤解しやすい   |

## 差分2：状態の扱いと更新方法

### 違い

| React | Vue |
| --- | --- |
| 各レンダーが持つ状態を、変更不能なスナップショットとして扱う。次の状態は更新関数へ新しい値を渡して作る | コンポーネントが保持する状態を、変更可能なリアクティブな状態として扱う。`ref`や`reactive`への書き込みをVueが検知する |

### Reactの動作

Reactでは、現在のレンダーが持つ状態を直接変更せず、更新関数へ次の値を渡す。

```tsx
const [enabled, setEnabled] = useState(false);

setEnabled(true);
```

booleanや数値などのプリミティブ値はもともと内部を変更できないため、新しい値へ置き換える。オブジェクトや配列の場合は、変更前のスナップショットを保つため、新しいオブジェクトや配列を作る。

```tsx
setUser((current) => ({
  ...current,
  name: "Alice"
}));
```

次のように既存の状態を直接変更しても、Reactへ新しいレンダーを要求したことにはならない。

```tsx
user.name = "Alice";
```

Reactはオブジェクト内部への代入を監視していないため、直接変更しただけでは再レンダーを要求したことにならない。

### Vueの動作

Vueでは、`ref`や`reactive`への書き込みをVueが検知し、その状態に依存する処理へ更新を通知する。

```ts
const enabled = ref(false);

enabled.value = true;
```

boolean自体を変更しているのではなく、`ref`が保持する値を置き換えている。オブジェクトや配列の場合は、リアクティブな状態のプロパティを直接変更できる。

```ts
const user = reactive({ name: "Bob" });

user.name = "Alice";
```

この代入はProxyのsetterに捕捉され、`user.name`に依存する処理へ更新が通知される。

### なぜ違うのか

| Reactの思想 | Vueの思想 |
| --- | --- |
| 各レンダーの状態を変更不能なスナップショットにし、いつ、どの更新によって値が変わったのかを明示する | 状態を変更可能なリアクティブ値として保持し、通常のJavaScriptに近い代入と画面更新を結び付ける |

#### React：状態変更を明示的にする

Reactは、あるレンダーが参照している状態が後から書き換わることで、「そのUIがどの時点の状態から作られたのか分からなくなる」という複雑性を避けようとしている。

そのため、各レンダーが持つ状態を変更不能なスナップショットとして扱い、更新関数へ次の値を渡して新しいレンダーを要求する。オブジェクトや配列では、変更前のスナップショットを残すために新しい値を作る必要がある。

この明示性を保つために、Reactではイミュータブル更新を開発者が行う必要がある。

#### Vue：状態更新の記述を直感的にする

Vueは、状態を変更したら、それに依存する表示も更新されるという直感的な操作を重視している。

そのため、状態を変更可能な`ref`や`reactive`として保持し、そこへの書き込みをVueが画面更新へつなげる。オブジェクトや配列では同じ値への直接変更も検知できるため、更新のたびに新しい値を作る必要がない。

つまり、Reactは「各レンダーの状態を変更不能なスナップショットにする」ことで複雑性を減らし、Vueは「変更可能な状態への書き込みをフレームワークが追跡する」ことで複雑性を減らしている。Vueでも、必要に応じてイミュータブルに更新できる。

### メリット・デメリット

|       | メリット                                                            | デメリット                                                                     |
| ----- | --------------------------------------------------------------- | ------------------------------------------------------------------------- |
| React | 変更前後の状態が分離されるため、参照比較、並行レンダー、更新履歴、Undoと相性がよい。過去のレンダーが参照する値も変化しない | ネストしたオブジェクトでは、新しいオブジェクトを階層ごとに作る必要があり記述量が増えやすい。直接変更しても再レンダーされないというミスが起こり得る |
| Vue   | 通常のJavaScript代入に近い書き方で、ネストした値も簡潔に更新できる。新しいオブジェクトを毎回作る必要がない      | ProxyやRefを経由しない値は変更を追跡できない。分割代入によるリアクティビティの切断など、監視される範囲を理解する必要がある         |

Reactは、状態を変更前後で分離する制約を開発者に求める代わりに、レンダーを独立したスナップショットとして扱いやすくする。

Vueは、Proxyによる監視をフレームワークが引き受ける代わりに、開発者が自然な代入形式で状態を変更できる。ただし、リアクティブな値と普通の値の境界を理解する必要がある。

## 差分3：状態を作る場所と所有者

### 違い

| React | Vue |
| --- | --- |
| `useState`などのHookは、関数コンポーネントまたはCustom Hookのトップレベルで呼ぶ。状態はレンダーツリー上のコンポーネントの位置に結び付く | `ref`や`reactive`はコンポーネント外でも作れる。作る場所によって、コンポーネント固有の状態にも、複数コンポーネントで共有する状態にもなる |

### Reactの動作

Reactのローカルな状態は、関数コンポーネントまたはCustom Hookのトップレベルで宣言する。

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount((current) => current + 1)}>
      {count}
    </button>
  );
}
```

ReactはHookを呼び出した順番によって、それぞれの状態をコンポーネントに対応付ける。そのため、Hookを条件分岐、ループ、イベントハンドラーの中で呼ぶことはできない。

状態はコンポーネント関数のローカル変数そのものに保存されるのではなく、Reactがレンダーツリー上の位置と対応付けて保持する。同じ`Counter`を2か所に配置すると、それぞれが独立した状態を持つ。コンポーネントがツリーから外れれば、その位置に対応する状態も破棄される。

Reactでも、コンポーネント外に外部ストアを作ることはできる。その場合は、`useSyncExternalStore`などを使ってコンポーネントを外部ストアへ購読させる。つまり、状態をコンポーネント外に置けないのではなく、React標準のローカルな状態と外部ストアを区別して扱う。

### Vueの動作

Vueの`ref`や`reactive`は、コンポーネントの内部だけでなく、通常のJavaScriptモジュールでも作れる。

`<script setup>`やComposableの関数内で状態を作ると、呼び出したコンポーネントインスタンスごとに新しい状態が作られる。

```ts
export function useLocalCounter() {
  const count = ref(0);

  return { count };
}
```

一方、モジュールスコープで作った状態は、同じモジュールを利用するコンポーネント間で共有される。

```ts
const sharedCount = ref(0);

export function useSharedCounter() {
  return { count: sharedCount };
}
```

Vueのリアクティビティはコンポーネントモデルから独立しているため、単純な共有状態であれば専用ストアを用意せず構成できる。ただし、SSRでモジュールスコープの状態を使うと、同じサーバープロセスが処理する複数リクエスト間で状態を共有する危険がある。

また、`ref`や`reactive`自体を作れる場所と、Composableを安全に呼べる場所は同じではない。ライフサイクルフックを登録したり、コンポーネントのアンマウント時にWatcherを自動破棄したりするComposableは、原則として`<script setup>`または`setup()`内で同期的に呼ぶ必要がある。

### なぜ違うのか

| Reactの思想 | Vueの思想 |
| --- | --- |
| 状態の所有者と寿命をコンポーネントツリー上で明確にし、どの状態がどのUIに属するかを予測しやすくする | リアクティビティをコンポーネントから分離し、状態を作る場所や再利用・共有する単位を柔軟に選べるようにする |

#### React：状態の所有者をコンポーネントツリーで明確にする

Reactは、「この状態はどのUIに属し、いつ作られ、いつ破棄されるのか分からなくなる」という複雑性を避けようとしている。

そのため、標準のローカルな状態をレンダーツリー上のコンポーネント位置へ結び付ける。Hookを同じ順番で呼ぶという制約を設けることで、Reactは状態とコンポーネントの対応を安定して管理できる。

複数コンポーネントで状態を共有するときは、共通の親へ状態を持ち上げる、Contextを使う、外部ストアへ購読するといった形で、所有場所を明示的に広げる。

#### Vue：状態の再利用・共有方法を柔軟にする

Vueは、状態を再利用・共有するために、必ずコンポーネントツリーへ結び付けたり専用の状態管理機構へ移したりする負担を減らそうとしている。

そのため、リアクティビティを独立した仕組みとして提供し、作成場所によって状態の所有単位を選べるようにしている。Composableの内側に作れば呼び出しごとの状態になり、外側に作れば共有状態になる。

つまり、Reactは「状態の所有者と寿命をコンポーネントツリー上で明示する」ことで複雑性を減らし、Vueは「リアクティビティをコンポーネントから分離する」ことで状態の構成方法を柔軟にしている。

### メリット・デメリット

| | メリット | デメリット |
| --- | --- | --- |
| React | 状態の所有者、分離単位、破棄される条件をコンポーネントツリーから追いやすい。各コンポーネントインスタンスの状態が意図せず共有されにくい | Hookを呼べる場所と順番に制約がある。ツリーをまたぐ共有状態では、状態の持ち上げ、Context、外部ストアなどを明示的に選ぶ必要がある |
| Vue | コンポーネント固有の状態と共有状態を、作成場所によって簡潔に構成できる。リアクティブなロジックを通常のJavaScriptモジュールへ切り出しやすい | 作成場所を誤ると、意図しないシングルトン状態になる。特にSSRではリクエスト間の状態共有に注意が必要で、状態の所有者や寿命がコードから見えにくくなる場合がある |

## 要約

| 差分 | React | Vue |
| --- | --- | --- |
| 状態更新時 | コンポーネント関数を再実行する | 依存するレンダー処理を実行する |
| 初期化処理 | 関数本体に含まれるため再実行される | 同じインスタンスの`<script setup>`は再実行されない |
| 普通の派生変数 | 再レンダー時に再計算される | 一度計算した値は`ref`へ自動追従しない |
| 状態変更 | 新しい値を更新関数へ渡す | ProxyやRefへの代入を検知する |
| オブジェクト更新 | イミュータブル更新が基本 | ミュータブルな更新を検知できる |
| 状態を作る場所 | 関数コンポーネントまたはCustom Hookのトップレベル | `ref`や`reactive`はコンポーネント外でも作れる |
| 状態の所有者 | レンダーツリー上のコンポーネント位置に結び付く | 作成場所によってコンポーネント固有または共有状態になる |
