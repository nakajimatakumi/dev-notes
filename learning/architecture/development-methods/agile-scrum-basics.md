# アジャイル開発とスクラムの基本

アジャイルは、最初にすべてを確定して計画どおりに作り切るのではなく、価値のある小さな成果を短い間隔で届け、利用者や市場から得た学びを次の計画へ反映する考え方である。目的は、単に開発速度を上げることではない。不確実性がある状況で、早く検証し、誤った方向へ大きく進むリスクを抑えながら、価値を継続的に高めることにある。

スクラムは、アジャイルの価値と原則を実践するための代表的なフレームワークである。このページでは、アジャイルの目的と基本サイクルを確認したうえで、スクラムの責任、作成物、イベントを体系的に整理する。

## アジャイルの目的

| 目的 | 進め方 |
| --- | --- |
| 顧客価値を早く届ける | 優先度の高い機能から、小さく動く状態で提供する。 |
| 不確実性を減らす | 仮説を実装し、利用者の反応や計測結果から学ぶ。 |
| 変化へ対応する | 定期的に優先順位と計画を見直し、新しい情報を反映する。 |
| 手戻りを小さくする | 短い間隔で成果物を確認し、認識違いや技術的な問題を早く発見する。 |
| 継続的に改善する | 成果物だけでなく、チームの協働方法や開発プロセスも振り返る。 |

アジャイルソフトウェア開発宣言は、右側の事柄に価値がないとするものではなく、両方に価値を認めたうえで左側をより重視するという判断基準を示している。

| より重視するもの | 対応するもの     |
| -------- | ---------- |
| 個人と対話    | プロセスやツール   |
| 動くソフトウェア | 包括的なドキュメント |
| 顧客との協調   | 契約交渉       |
| 変化への対応   | 計画に従うこと    |

したがって、アジャイルでは計画や文書を作らないわけではない。意思決定、開発、運用に必要な分だけ作り、得られた情報に応じて更新する。

## 基本的な進め方

アジャイル開発では、次のサイクルを短い間隔で繰り返す。

1. **目的を定める**: 解決したい利用者の課題、提供したい価値、評価方法を明確にする。
2. **作業候補を並べる**: 機能、改善、調査、不具合対応などを、価値と必要性が分かる単位で整理する。
3. **優先順位を決める**: 価値、リスク、依存関係、作業量を踏まえ、次に取り組む項目を選ぶ。
4. **小さく計画する**: 短い期間で達成する目標と、そのために必要な作業を決める。
5. **設計・実装・テストする**: 完成の基準を守り、利用可能な成果を作る。
6. **成果を確認する**: 利用者やステークホルダーと結果を確認し、環境の変化や新しい要求を把握する。
7. **進め方を改善する**: チームの協働、品質、開発プロセスを振り返り、次に試す改善を決める。
8. **学びを反映する**: 作業候補と優先順位を更新し、次のサイクルへ進む。

このサイクルでは、すべての要求を最初に細部まで固定する必要はない。一方で、プロダクトの目的、法令、予算、期限、セキュリティなどの制約まで無視してよいわけではない。変えられるものと変えられないものを区別する。

## アジャイルとスクラムの関係

| 用語 | 位置づけ |
| --- | --- |
| アジャイル | 価値観と原則に基づき、反復的・漸進的に価値を届ける考え方。 |
| スクラム | 複雑な問題に対して価値を生み出すための、軽量なフレームワーク。 |
| カンバン | 作業の流れを可視化し、仕掛かりを制限してフローを改善する方法。 |
| XP | ペアプログラミング、継続的インテグレーション、TDDなど、技術的な実践を重視する開発手法。 |

スクラムを採用することだけでアジャイルになるわけではない。イベントを予定どおり開催していても、成果を検査せず、計画を適応させず、顧客価値より作業消化を優先していれば、アジャイルの目的から外れる。

## スクラムの全体像

スクラムは、経験から学んで判断する経験主義と、必要なものだけに集中するリーン思考を基礎とする。経験主義を機能させる3本柱は次のとおりである。

| 柱 | 意味 |
| --- | --- |
| 透明性 | 作業や成果物の重要な状態を、関係者が共通に理解できるようにする。 |
| 検査 | 目標への進捗と成果物を頻繁に確認し、問題や望ましくない差異を見つける。 |
| 適応 | 検査で得た学びをもとに、成果物や進め方をできるだけ早く調整する。 |

スクラムチームは、**確約、集中、公開、尊敬、勇気**という5つの価値基準を行動の判断に用いる。

スクラムの構成要素は、3つの責任、3つの作成物とその確約、5つのイベントとして整理できる。

| 区分 | 構成要素 |
| --- | --- |
| 責任 | プロダクトオーナー、スクラムマスター、開発者 |
| 作成物 | プロダクトバックログ、スプリントバックログ、インクリメント |
| 作成物への確約 | プロダクトゴール、スプリントゴール、完成の定義 |
| イベント | スプリント、スプリントプランニング、デイリースクラム、スプリントレビュー、スプリントレトロスペクティブ |

## スクラムチームの3つの責任

スクラムチームは、1人のプロダクトオーナー、1人のスクラムマスター、複数の開発者で構成する。チーム内に上下関係やサブチームを設けず、1つのプロダクトゴールへ集中する。一般に10人以下の小さなチームとし、価値を生み出すために必要な能力をチーム全体で持つ。

### プロダクトオーナー

プロダクトの価値を最大化し、プロダクトバックログを効果的に管理する責任を持つ。

- プロダクトゴールを設定し、明示する。
- プロダクトバックログ項目を分かりやすく表現し、並べ替える。
- バックログが透明で、見える状態になっていることを保証する。
- 関係者の要望を集約し、最終的な優先順位を判断する。

作業をほかの人へ委任しても、説明責任はプロダクトオーナーに残る。委員会ではなく1人が責任を持つが、独断で進めるという意味ではなく、利用者やステークホルダーとの継続的な対話が必要である。

### スクラムマスター

Scrum Guideに定義されたスクラムを確立し、スクラムチームと組織の有効性を高める責任を持つ。

- チームが自己管理と機能横断性を高められるよう支援する。
- 価値の高いインクリメントの作成に集中できるよう支援する。
- チームの進捗を妨げる障害の除去を促す。
- スクラムイベントが目的を満たし、時間枠内で行われるようにする。
- プロダクトオーナーや組織にもスクラムの理解と導入を支援する。

スクラムマスターは、メンバーへ作業を割り当てるプロジェクトマネージャーや、会議の司会だけを担当する役割ではない。

### 開発者

各スプリントで、利用可能なインクリメントを作ることに確約する人たちである。プログラマーだけを指す名称ではなく、テスト、設計、分析など、完成に必要な専門性を持つメンバーを含む。

- スプリントバックログという計画を作る。
- 完成の定義を守って品質を作り込む。
- スプリントゴールに向けて毎日計画を調整する。
- 専門家として互いに責任を持つ。

## 3つの作成物と確約

### プロダクトバックログとプロダクトゴール

プロダクトバックログは、プロダクトを改善するために必要な作業を順序づけた、唯一の一覧である。要求、機能、技術的改善、不具合、調査などを含められる。

プロダクトゴールは、プロダクトの将来の状態を表す長期的な目標である。チームは、現在のプロダクトゴールを達成または放棄してから、次のゴールへ進む。

### スプリントバックログとスプリントゴール

スプリントバックログは、次の3つから構成される開発者の計画である。

- **なぜ**: スプリントゴール。
- **何を**: スプリントで選択したプロダクトバックログ項目。
- **どのように**: インクリメントを届けるための実行可能な計画。

スプリントゴールは、スプリントの単一の目的である。実現方法には柔軟性を残しつつ、チームが同じ目的に集中できるようにする。

### インクリメントと完成の定義

インクリメントは、プロダクトゴールへ向かう具体的な一歩であり、それまでのインクリメントと統合され、利用可能な状態でなければならない。1つのスプリントで複数のインクリメントを作成・提供してもよい。

完成の定義（Definition of Done）は、インクリメントが満たすべき品質基準を明文化したものである。例えば、コードレビュー、自動テスト、セキュリティ確認、ドキュメント更新、対象環境への統合などを含む。完成の定義を満たさない作業はインクリメントの一部ではなく、レビューで完成扱いにできない。

## 5つのスクラムイベント

スプリントはほかの4イベントを内包する。各イベントは、作成物を検査して適応するための公式な機会であり、単なる進捗報告会ではない。時間枠は1か月のスプリントに対する上限で、短いスプリントでは通常さらに短くする。

| イベント | 主な目的 | 主な参加者 | 1か月スプリントの時間枠 | 主な結果 |
| --- | --- | --- | --- | --- |
| スプリント | アイデアを価値へ変える | スクラムチーム | 1か月以内 | 完成したインクリメントと学び |
| スプリントプランニング | スプリントで行う作業を開始する | スクラムチーム全員 | 最大8時間 | スプリントゴールとスプリントバックログ |
| デイリースクラム | ゴールへの進捗を検査し、次の1日の計画を調整する | 開発者 | 15分 | 更新された実行計画 |
| スプリントレビュー | スプリントの成果と環境変化を検査し、今後を適応する | スクラムチームと主要なステークホルダー | 最大4時間 | 次に行うことと更新されたバックログ |
| スプリントレトロスペクティブ | 品質と有効性を高める改善を計画する | スクラムチーム | 最大3時間 | 次に試す具体的な改善 |

### スプリント

スプリントは、1か月以内の固定した長さで連続して行う。前のスプリントが終了すると、次のスプリントが直ちに始まる。

スプリント中は、スプリントゴールを危険にさらす変更を行わず、品質を低下させない。一方、学びが増えたらプロダクトバックログをリファインメントし、スコープについてプロダクトオーナーと開発者が交渉できる。スプリントゴールが役に立たなくなった場合に限り、プロダクトオーナーがスプリントを中止できる。

### スプリントプランニング

スクラムチーム全員で、次の3つの話題を扱う。

1. **このスプリントはなぜ価値があるのか**: プロダクトゴールや優先順位を踏まえてスプリントゴールを決める。
2. **このスプリントで何ができるのか**: 過去の実績、能力、完成の定義を考慮し、取り組むバックログ項目を開発者が選ぶ。
3. **選択した作業をどのように成し遂げるか**: 完成したインクリメントにするため、作業方法を開発者が計画する。

### デイリースクラム

開発者がスプリントゴールへの進捗を確認し、次の1日に向けて計画を調整する。毎営業日、同じ時刻・場所で15分間行う。特定の3つの質問を順番に答える形式は必須ではなく、ゴールへの進捗に焦点を当て、実行可能な計画を作れれば形式は開発者が選べる。

上司やスクラムマスターへ個人の作業状況を報告する場ではない。詳細な問題解決が必要なら、関係者だけでデイリースクラム後に続ける。

### スプリントレビュー

スクラムチームと主要なステークホルダーが、完成した成果とプロダクトゴールへの進捗、利用状況、市場や業務環境の変化を一緒に検査する。その結果をもとに次に行うことを話し合い、必要ならプロダクトバックログを更新する。

完成したものを一方的に説明するデモや承認会に限定しない。成果を材料に、今後の選択肢を共同で検討する作業セッションである。

### スプリントレトロスペクティブ

個人、対話、プロセス、ツール、完成の定義について、前のスプリントを検査する。うまくいったこと、問題、原因、すでに解決したことを確認し、品質と有効性を高める変更を選ぶ。

改善案を多く挙げるだけで終わらせず、影響が大きく次のスプリントで実行できるものを具体化する。必要なら次のスプリントバックログへ追加する。

## バックログリファインメント

バックログリファインメントは、プロダクトバックログ項目をより小さく具体的にし、説明、順序、作業規模などの情報を追加する継続的な活動である。将来の項目を理解し、プランニングで選択できる状態に近づける。

Scrum Guideでは正式なスクラムイベントではなく、固定の会議名や時間枠も定められていない。チームは必要に応じてスプリント中に行う。詳細を早く決めすぎると変更コストが増えるため、近く着手する項目ほど具体化する。

## 2週間スプリントの進行例

| 時点 | 活動 | 確認すること |
| --- | --- | --- |
| 開始日 | スプリントプランニング | ゴール、選択項目、完成へ進む計画を合意する。 |
| 毎営業日 | デイリースクラム | ゴールへの進捗と次の1日の計画を調整する。 |
| スプリント中 | 設計・実装・テスト、リファインメント | 完成の定義を守り、必要に応じて計画と将来の項目を更新する。 |
| 最終日 | スプリントレビュー | 完成した成果と環境変化を検査し、今後の優先順位へ反映する。 |
| 最終日 | スプリントレトロスペクティブ | チームの進め方を検査し、次の改善を決める。 |
| 直後 | 次のスプリント | 更新したバックログをもとに、次のサイクルを始める。 |

設計、実装、テストをスプリント内で順番に別担当へ受け渡すのではなく、項目ごとに協力して完成へ進める。スプリント末尾にテストだけをまとめると、未完成の作業が積み上がり、検査と適応が遅れる。

## 進捗と成果の見方

アジャイルでは、作業量を増やすことより、価値のある成果と学習を重視する。

| 観点 | 例 |
| --- | --- |
| 顧客・事業成果 | 利用率、完了率、問い合わせ削減、リードタイム、売上など、プロダクトゴールに対応する指標。 |
| 成果物 | 完成の定義を満たし、利用可能になったインクリメント。 |
| フロー | 着手から完了までの時間、仕掛かり数、完了量、ブロック時間。 |
| 品質 | 本番障害、欠陥流出率、変更失敗率、復旧時間、技術的負債。 |
| チーム改善 | レトロスペクティブで決めた改善の実施結果と、持続可能なペース。 |

ベロシティや消化ポイントは、チームが将来の作業量を予測するための補助情報であり、顧客価値そのものではない。個人評価やチーム間比較の目標にすると、見積もりを大きくする行動を促し、品質や成果を見えにくくする。

## よくある誤解と失敗

| 誤解・失敗 | 問題 | 改善の方向 |
| --- | --- | --- |
| アジャイルは計画や文書を作らない | 判断根拠や制約が共有されず、手戻りが増える。 | 必要十分な計画・文書を作り、学びに応じて更新する。 |
| スプリントは短い納期である | 完了できない作業を詰め込み、品質を下げやすい。 | スプリントゴールを中心に、達成可能な量を選ぶ。 |
| デイリーは上司への報告会である | 開発者が自ら計画を調整できない。 | ゴールへの進捗と、次の行動の調整に集中する。 |
| レビューは完成報告や承認会である | ステークホルダーから学び、次を適応する機会を失う。 | 成果と環境変化を材料に、次の選択肢を共同検討する。 |
| レトロスペクティブは反省会である | 個人への責任追及になり、問題が共有されなくなる。 | 仕組みと協働方法を対象に、小さな改善実験を決める。 |
| 未テストでもスプリント末に完成扱いする | 利用可能な成果が増えず、本当の進捗が分からない。 | 完成の定義を明確にし、満たしたものだけをインクリメントとする。 |
| 要求変更をいつでも無条件に追加する | 集中が崩れ、スプリントゴールを達成できない。 | ゴールを守りながらスコープを交渉し、将来分はバックログへ反映する。 |

## 導入時に最初に決めること

1. プロダクトが解決する課題と、最初のプロダクトゴールを明文化する。
2. プロダクトオーナー、スクラムマスター、開発者を明確にする。
3. プロダクトバックログを1つに集約し、価値に基づいて並べる。
4. 1か月以内のスプリント期間と、各イベントの日程を決める。
5. チーム共通の完成の定義を作る。
6. 最初のスプリントゴールを定め、小さく利用可能な成果を選ぶ。
7. レビューで誰から何を学ぶか、成果指標をどう確認するか決める。
8. レトロスペクティブで改善を1つ選び、次のスプリントで試す。

最初から複雑なチケット運用や多数の指標を導入するより、目的、透明なバックログ、完成の定義、検査と適応の習慣を優先する。
