# 「〜駆動開発」の種類と使い分け

「〜駆動開発」とは、開発で何を判断の中心に置くかを表す呼び方である。ただし、すべてが同じ粒度の開発手法ではない。ドメイン駆動開発は業務の理解と設計、テスト駆動開発はコードを書く手順、仕様駆動開発は仕様から実装へ進む流れを主に扱う。そのため、どれか1つだけを選ぶのではなく、目的に応じて併用できる。

このページでは代表的な7種類を扱う。「データ駆動」「ユーザー駆動」などの表現も使われるが、組織ごとに意味が異なる場合があるため、ここでは比較的定義が明確な手法に絞る。

## ドメイン駆動開発（DDD）

Domain-Driven Designは、対象業務の知識やルールを表すドメインモデルを、ソフトウェア設計の中心に置く考え方である。ドメインエキスパートと開発者が共通の言葉であるユビキタス言語を育て、大きな業務領域を境界づけられたコンテキストに分割する。

- 目的: 複雑な業務ルールを、業務上の概念と一致したコードやモデルで表現する。
- 主な運用: 業務担当者との対話、用語集やモデルの更新、コンテキスト境界の整理を継続する。
- 主な成果物: ユビキタス言語、ドメインモデル、コンテキストマップ、モデルを反映したコード。
- 向いている場面: 業務ルールが複雑で、用語の解釈差や変更が設計へ大きく影響するシステム。
- 注意点: 単純なCRUDや業務知識が少ない機能では、導入コストが効果を上回ることがある。

## テスト駆動開発（TDD）

Test-Driven Developmentは、実装前に小さな自動テストを書き、失敗を確認してから最小限の実装で通し、その後に設計を改善する手順である。一般に「Red → Green → Refactor」の短いサイクルを繰り返す。

- 目的: 動作を小さく確認しながら、変更しやすい設計と回帰テストを作る。
- 主な運用: 開発者が数分程度の短い単位で、失敗するテスト、実装、リファクタリングを反復する。
- 主な成果物: ユニットテスト、テストしやすく分割されたコード。
- 向いている場面: 入出力やルールを小さな例で表せ、継続的に変更するコード。
- 注意点: テストを後から追加することや、テスト件数を増やすことだけではTDDにならない。UIの見た目や探索的な試作など、先に期待結果を固定しにくい作業には適用しづらい。

## 振る舞い駆動開発（BDD）

Behavior-Driven Developmentは、利用者や業務から見たシステムの振る舞いを具体例で合意し、その例から実装と自動テストを進める方法である。Cucumberでは、発見、定式化、自動化の3つの実践として説明されている。

- 目的: 業務担当者、開発者、テスト担当者の「何を作るか」という認識を揃える。
- 主な運用: 会話から具体例を発見し、Given-When-Thenなどの読める形に整理し、必要な例を自動化する。
- 主な成果物: 振る舞いの具体例、シナリオ、実行可能な仕様。
- 向いている場面: 業務フローや条件分岐を、複数の役割で確認する必要がある機能。
- 注意点: Gherkinを書くことだけが目的ではない。会話による発見を省くと、読みにくいE2Eテストだけが増えやすい。

## 受入テスト駆動開発（ATDD）

Acceptance Test-Driven Developmentは、実装前に顧客・開発・テストなど異なる視点の担当者が受入テストを共同で作り、完成条件として使う方法である。BDDやSpecification by Exampleと重なる部分が多いが、ATDDは特に「受け入れられる条件」を先に決めることへ焦点を置く。

- 目的: ストーリーや機能の完成条件を、利用者の視点で検証可能にする。
- 主な運用: 実装前に具体的な入力、操作、期待結果を合意し、実装中と完了時に確認する。
- 主な成果物: 受入条件、受入テスト、必要に応じて自動化された機能テスト。
- 向いている場面: 顧客受入やプロダクトオーナーとの合意が重要な機能開発。
- 注意点: UI操作だけに依存したテストは壊れやすい。自動化ツールより、完成条件を共同で明確にする会話を優先する。

## 仕様駆動開発（SDD）

Specification-Driven Developmentは、実装前に「何を作るか」を仕様として明文化し、設計、タスク分解、実装、検証の基準にする方法である。特に近年のAI開発では、仕様をAIコーディングエージェントへ渡す持続的なコンテキストとして扱い、`Spec → Plan → Tasks → Implement`のように段階的に成果物を作る用法が広がっている。

具体的な成果物と運用手順は、[仕様駆動開発の進め方](./spec-driven-development-guide.md)にまとめる。

- 目的: 要求、設計判断、実装範囲を明示し、実装の逸脱や会話ごとの文脈消失を減らす。
- 主な運用: 機能ごとに仕様を作成・レビューし、設計とタスクへ分解してから実装する。変更時はコードだけでなく仕様も更新する。
- 主な成果物: 要求仕様、受入条件、設計、実装計画、タスクリスト。
- 向いている場面: AIへ複数工程を任せる開発、複数人で判断を共有する開発、影響範囲の広い機能。
- 注意点: SDDには単一の標準定義がなく、ツールごとに工程や仕様の厳密さが異なる。仕様が曖昧または古いままなら、AIはその誤りも効率よく実装してしまう。

## 機能駆動開発（FDD）

Feature-Driven Developmentは、顧客価値のある小さな機能を単位として、モデル作成、機能一覧、計画、機能ごとの設計と構築を進める反復型の開発プロセスである。

- 目的: 大きな開発を小さな機能へ分け、進捗と完成を機能単位で把握する。
- 主な運用: 全体モデルと機能一覧を作り、機能単位で計画し、「Design by Feature」「Build by Feature」を繰り返す。
- 主な成果物: 全体モデル、機能一覧、機能別計画、設計パッケージ、動作する機能。
- 向いている場面: 機能を短い単位へ分割でき、チーム全体の進捗を揃えて管理したい比較的大きな開発。
- 注意点: 単にチケットを機能名で分けるだけではFDDのプロセスにはならない。古典的FDDの役割やオブジェクトモデルを、そのまま現代の小規模チームへ適用する必要もない。

## モデル駆動開発（MDD）

Model-Driven Developmentは、図や形式的なモデルを主要な開発成果物として扱い、モデル変換やコード生成によって実装へつなげる考え方である。代表的な体系であるOMGのModel Driven Architectureでは、プラットフォーム非依存モデルをプラットフォーム固有モデルやコードへ変換する。

- 目的: 業務・設計と特定技術を分離し、生成や変換によって一貫性と再利用性を高める。
- 主な運用: メタモデルと記法を定め、モデルを更新し、変換・生成結果を検証する。モデルを正本として保つ。
- 主な成果物: UMLなどのモデル、変換規則、生成コード、プラットフォーム固有モデル。
- 向いている場面: 定型的な構造が多い、複数プラットフォームへ展開する、長期的に同じモデル資産を使うシステム。
- 注意点: モデルと手書きコードの二重管理、生成ツールへの依存、例外的な実装の扱いが課題になる。

## 比較

AIとの親和性は手法自体の優劣ではなく、AIへ渡せる明示的な入力があるか、出力を機械的に検証できるかで評価している。評価は「高・中・低」の相対的な目安である。

| 手法   | 判断の中心         | 主な目的               | 日常の運用単位                              | AIとの親和性 | 親和性と注意点                                                     |
| ---- | ------------- | ------------------ | ------------------------------------ | ------- | ----------------------------------------------------------- |
| DDD  | 業務知識とドメインモデル  | 複雑な業務を正しく設計する      | 用語・モデル・境界の継続的な対話                     | 中〜高     | 用語集やモデルは良い文脈になる。一方、暗黙知の発見や境界の妥当性判断は人の業務理解が必要。               |
| TDD  | 失敗する小さなテスト    | コードの動作と設計を短周期で改善する | Red → Green → Refactor               | 高       | テストが即時フィードバックになる。ただしAIが誤ったテストと実装を同時に作る可能性があるため、期待値のレビューが必要。 |
| BDD  | 利用者から見た振る舞いの例 | 関係者の共通理解を作る        | 発見 → 定式化 → 自動化                       | 高       | 具体例はプロンプトと検証条件の両方になる。AIだけで例を作ると、業務上重要な例外を見落としやすい。           |
| ATDD | 合意した受入条件      | 完成条件を実装前に明確にする     | 機能・ストーリーごとの受入テスト                     | 高       | AIの実装を受入条件で検証しやすい。受入条件そのものの合意は顧客・チームが担う。                    |
| SDD  | 明文化された仕様      | 仕様から設計・実装までの逸脱を減らす | Spec → Plan → Tasks → Implement      | 非常に高い   | 仕様をAIの持続的なコンテキストにできる。仕様の品質、更新、コードとのずれを人と自動検査で管理する必要がある。     |
| FDD  | 顧客価値のある小さな機能  | 機能単位で計画・設計・進捗管理する  | Design by Feature → Build by Feature | 中       | 機能一覧と小さな作業単位はAIへ委任しやすい。機能間の統合や全体モデルの整合性は別途管理が必要。            |
| MDD  | 形式化されたモデル     | モデルから一貫した実装を生成する   | モデル作成 → 変換 → 生成・検証                   | 中〜高     | 構造化モデルは曖昧さが少なく生成と相性がよい。AIの自由生成より、決定的な変換器との役割分担が重要。          |

### 違いを短く捉える

- DDDは「業務をどう理解し、コードの概念へ反映するか」を駆動する。
- TDDは「次に書くコードと設計改善」をテストで駆動する。
- BDDとATDDは「関係者が合意する振る舞い・完成条件」を具体例で駆動する。
- SDDは「仕様から設計、タスク、実装へ進む一連の作業」を駆動する。
- FDDは「何をどの単位で計画し、完成として数えるか」を機能で駆動する。
- MDDは「設計情報から実装をどう変換・生成するか」をモデルで駆動する。

## 併用例

AIを利用した業務システム開発では、次のように組み合わせられる。

1. DDDで業務用語、ルール、境界を整理する。
2. SDDで対象機能の要求、設計、タスクを明文化する。
3. BDDまたはATDDで利用者視点の具体例と受入条件を合意する。
4. AIにタスク単位の実装を依頼し、TDDの短いサイクルでコードを検証する。
5. 機能単位で統合し、仕様・テスト・コードのずれをレビューする。

この組み合わせでは、AIに「自由に正解を考えさせる」のではなく、人が業務上の目的と判断基準を定め、AIには明示された範囲の生成・修正・検証を担当させる。

## 選び方

| 困っていること | 最初に検討する手法 |
| --- | --- |
| 業務用語やルールの解釈が人によって違う | DDD |
| コード変更のたびに不具合が入りやすい | TDD |
| 要求が抽象的で、担当者間の認識が合わない | BDD |
| 完成・受入の判定が曖昧 | ATDD |
| AIが実装途中で目的や制約から逸脱する | SDD |
| 大規模開発の進捗を機能単位で把握したい | FDD |
| 同じ設計から複数環境向けの実装を生成したい | MDD |
