# 仕様駆動開発の進め方

仕様駆動開発（Specification-Driven Development、SDD）は、作りたいものの意図を仕様として明文化し、その仕様から設計、タスク、実装、検証を一貫して導く開発方法である。特にAIを利用した開発では、その場の会話ではなく、リポジトリに保存された仕様を継続的なコンテキストとして使う。

中心となる考え方は、コードを書く前にすべてを完全に決めることではない。「何を満たすべきか」「何を対象外とするか」「どう確認するか」を実装に着手できる程度まで明確にし、実装で得た知見を仕様へ戻しながら反復する。

SDDには単一の標準定義がない。GitHub Spec Kit、Kiro、OpenSpecなどで成果物の名前や工程は異なる。このページでは、複数のツールに共通する考え方を扱う。

## 何を「仕様」と呼ぶか

SDDにおける仕様は、画面項目を網羅した1つの巨大な文書だけを指すものではない。目的ごとに分けた複数の成果物の集合として管理する。

| 成果物 | 答える問い | 主な内容 |
| --- | --- | --- |
| プロジェクト原則 | 常に守ることは何か | アーキテクチャ、セキュリティ、テスト、命名、禁止事項 |
| 機能仕様 | 何を、なぜ作るか | 目的、利用者、範囲、要求、受入条件、成功指標 |
| 設計・実装計画 | どう実現するか | 構成、データ、API、依存関係、技術選定、リスク |
| タスクリスト | どの順番で作るか | 実装単位、依存関係、対象ファイル、検証方法 |
| テスト・検証結果 | 仕様を満たしたか | 自動テスト、受入確認、静的解析、レビュー結果 |

「要求」と「設計」を分けることが重要である。機能仕様では利用者に必要な結果を定め、設計ではその結果を実現する技術的な方法を定める。技術を変えても要求が変わらないなら、要求側へフレームワーク名やクラス構造を書かない。

## 仕様駆動と呼べる状態

仕様書が存在するだけでは、仕様駆動とは限らない。次の状態が揃っていることが目安になる。

- 実装前に対象範囲と受入条件を確認している。
- 設計とタスクが、どの要求を実現するか追跡できる。
- AIと人が同じ版の仕様を参照している。
- 実装結果をテストやレビューで仕様と照合している。
- 要求変更時に、コードだけでなく仕様と関連成果物も更新している。
- 仕様とコードが矛盾した場合の扱いが決まっている。

SDDでは仕様を「意図の正本」として扱う。ただし、本番環境で実際に動く振る舞いはコードによって決まる。仕様を正本と宣言するだけでなく、テスト、トレーサビリティ、レビューによって両者のずれを検出する必要がある。

## 基本的な進め方

代表的な流れは、`Spec → Plan → Tasks → Implement`である。実務では、その前後に明確化と検証を加える。

### 1. プロジェクトの前提を共有する

機能ごとに繰り返さない共通ルールを用意する。

- 採用済みの技術とバージョン
- アーキテクチャとモジュール境界
- セキュリティ、個人情報、監査上の制約
- テスト方針と完了条件
- コーディング規約、既存実装の参照先
- 実行すべき確認コマンド

この情報がないと、AIは機能仕様を満たしていても、プロジェクトの慣習に反する実装を生成しやすい。

### 2. 機能仕様を作る

最初は「何を」「なぜ」に集中し、実装方法を混ぜない。

| 項目 | 確認する内容 |
| --- | --- |
| 背景・目的 | 誰の、どの問題を解決するか |
| 利用者 | 誰が利用・操作するか |
| 対象範囲 | 今回作るものと作らないもの |
| 要求 | 利用者やシステムが何をできる必要があるか |
| 受入条件 | どの条件と結果なら要求を満たしたと判断できるか |
| 非機能条件 | 性能、可用性、セキュリティ、運用など |
| 成功指標 | リリース後の価値をどう測るか |
| 前提・依存 | 既存機能、外部サービス、未確定事項 |

### 3. 曖昧さと不足を明確にする

- 「速い」「適切に」など、判定できない表現はないか。
- 権限、境界値、エラー、同時操作、再実行をどう扱うか。
- 対象外が明確か。
- 要求同士が矛盾していないか。
- 仮定と合意済みの事実を区別しているか。
- 受入条件を第三者が同じ結果で確認できるか。

すべてのケースを網羅することが目的ではない。正常な代表例、重要な例外、判断が分かれる境界を優先し、実装の方向が変わる不明点を先に解消する。

### 4. 設計・実装計画へ変換する

合意した要求を技術的な実現方法へ変換する。

- 既存コードの変更箇所
- コンポーネントやモジュールの責務
- データモデルと状態遷移
- APIやイベントの契約
- エラー処理、排他、再試行
- テスト戦略
- 移行、監視、ロールバック
- 技術選定とその理由

設計判断には、対応する要求IDや受入条件を記載する。要求から説明できない設計は、過剰実装または別の要求が隠れている可能性がある。

### 5. 実行可能なタスクへ分解する

各タスクは、AIまたは担当者が対象範囲と完了を判断できる大きさにする。

- 対応する要求またはユーザーストーリー
- 変更する責務と対象ファイル
- 先に完了すべき依存タスク
- 実装する内容
- 実行するテストや確認方法
- 完了と判断する条件

「認証機能を実装する」のような大きなタスクではなく、「失敗回数を記録する」「上限到達時にアカウントをロックする」「ロック時のAPI契約テストを追加する」のように、独立して確認できる単位へ分ける。

### 6. 成果物間の整合性を確認する

```text
目的
  ↓
要求・受入条件
  ↓
設計・API・データ
  ↓
実装タスク
  ↓
コード・テスト
```

- すべての要求に設計とタスクがあるか。
- 対応する要求がないタスクや設計がないか。
- 受入条件を確認するテストまたはレビュー方法があるか。
- プロジェクト原則に反する設計がないか。
- タスクの順序と並行実行可否が正しいか。

リスクが高い場合は仕様承認と設計承認を明示的なゲートにする。小さく定型的な変更では、同じ成果物を作り、まとめてレビューする軽量な運用もできる。

### 7. タスク単位で実装・検証する

1. 対象タスクと関連する要求・設計を読む。
2. 既存コードとテストを確認する。
3. 必要なテストと実装を追加する。
4. 指定された確認コマンドを実行する。
5. 差分がタスクの範囲内か確認する。
6. タスクの状態と検証結果を記録する。

実装途中で仕様の不足が分かった場合は、AIに推測だけで進めさせない。影響が小さく妥当な既定値なら仮定として記録し、業務、セキュリティ、データ損失などに影響する判断なら仕様へ戻して合意する。

### 8. 仕様と実装を同期する

- 受入条件を満たしている。
- 対象外の機能を追加していない。
- 設計変更が仕様または設計書へ反映されている。
- テストと運用手順が最新である。
- 未解決の仮定や既知の制約が記録されている。

## 具体例: 申請の下書き保存

### 最初の依頼

```text
申請者が入力途中の申請を下書き保存できるようにしたい。
```

この依頼だけでは、誰が何を保存できるか、競合をどう扱うか、保存成功をどう確認するかが分からない。

### 機能仕様

| ID | 内容 |
| --- | --- |
| 目的 | 入力途中の内容を失わず、後から申請を再開できるようにする。 |
| FR-001 | 申請者は、自分が作成した未提出の申請を下書き保存できること。 |
| FR-002 | 提出済みまたは承認済みの申請は、下書き保存できないこと。 |
| FR-003 | 保存の競合を検出し、他の更新を黙って上書きしないこと。 |
| 対象外 | 自動保存、共同編集、添付ファイルの一時保存。 |

受入条件の例:

```text
Given: 申請者が自分の未提出申請を編集中である
When: 下書き保存を実行する
Then: 入力内容が保存され、再表示すると同じ内容を確認できる

Given: 別の画面ですでに同じ申請が更新されている
When: 古い状態から下書き保存を実行する
Then: 上書きせず、最新状態の再読み込みを求める
```

### 設計・実装計画

| 要求 | 設計判断 |
| --- | --- |
| FR-001 | `PATCH /applications/{id}/draft`で更新し、所有者と状態をサーバー側で検証する。 |
| FR-002 | 状態が`draft`以外なら業務エラーを返す。画面のボタン非表示だけに依存しない。 |
| FR-003 | requestへ`version`を含め、楽観ロックで競合を検出する。 |

### タスク

```text
- T001: 下書き更新APIのrequest・response契約を定義する
- T002: 所有者と申請状態を検証するドメイン処理を追加する
- T003: versionによる楽観ロックと競合テストを追加する
- T004: 保存ボタンと成功・競合メッセージを実装する
- T005: 受入条件に対応する結合テストを実行する
```

依頼文をそのままAIへ渡すのではなく、要求、受入条件、設計、タスクの順に具体化する。各段階で人が方向を確認でき、実装後はFR-001〜003を満たしたか追跡できる。

## 仕様が変わったときの扱い

| 状況 | 最初に確認・更新するもの | その後の対応 |
| --- | --- | --- |
| 利用者の要求が変わった | 機能仕様と受入条件 | 影響する設計、タスク、テスト、コードを更新する。 |
| 技術的な制約が判明した | 設計と制約 | 要求を満たせない場合だけ、機能仕様へ戻って代替案を合意する。 |
| 実装が仕様と違っていた | どちらが正しいかを判断 | バグならコードを直し、仕様変更なら仕様を先に承認する。 |
| 内部構造だけを改善する | 設計とテスト | 外部の振る舞いが同じなら、要求を変えずにリファクタリングする。 |
| 緊急修正を先に行った | コード差分と事後仕様 | 修正後すぐに仕様・テストを同期する。 |

仕様を変更したら、下流成果物をすべて作り直す必要があるとは限らない。要求IDや対応表を使い、影響する設計、タスク、テストだけを更新する。

## AIと人の役割分担

| 作業 | AIが得意なこと | 人が担う判断 |
| --- | --- | --- |
| 仕様作成 | たたき台、表現の統一、不足候補の列挙 | 解決する価値、優先度、対象範囲の決定 |
| 明確化 | 曖昧語、矛盾、境界・異常系の候補抽出 | 業務上の正解、許容するリスクの決定 |
| 設計 | 既存コードの調査、代替案、影響範囲の整理 | アーキテクチャ、セキュリティ、運用上の承認 |
| タスク分解 | 依存関係、並行作業、確認手順の提案 | 分割の妥当性、担当、リリース順の決定 |
| 実装 | 定型コード、テスト、修正、コマンド実行 | 重要差分のレビュー、例外判断、受入 |
| 同期 | 仕様とコードの差分候補、追跡表の更新 | 仕様変更か実装不備かの最終判断 |

AIが生成した仕様、テスト、実装が同じ誤解に基づいて整合している場合もある。AIはフィードバックを高速化するが、業務上の正解や重要な受入判断は人が担う。

## プロトタイプとの関係

プロトタイプはSDDの必須成果物ではないが、仕様を明確にする手段として使える。

- 画面の配置や操作感を確認するプロトタイプを、仕様の補助資料にする。
- 技術的な実現可能性を確認するスパイクの結果を、設計判断へ反映する。
- プロトタイプで合意した内容を、画像だけに残さず要求や受入条件へ言語化する。
- 捨てる前提のコードを本番へ流用する場合は、設計・テスト・品質基準を確認し直す。

プロトタイプが「見た目や操作を探索するもの」なのに対し、仕様は「最終的に何を満たせばよいかを判断する基準」である。

## 他の進め方との違い

| 進め方 | 主な判断材料 | SDDとの関係 |
| --- | --- | --- |
| 通常の設計書中心開発 | 担当者が読む要求・設計文書 | 文書を参考資料で終わらせず、タスク、AI入力、検証までつなげる点が異なる。 |
| 会話中心のAI開発 | その場のプロンプトと生成結果 | SDDは意図と判断を永続的な成果物に残し、セッションを越えて再利用する。 |
| BDD | 利用者から見た振る舞いの具体例 | BDDのシナリオをSDDの受入条件として取り込める。 |
| TDD | 失敗する小さな自動テスト | SDDで決めた要求を、実装時にTDDで細かく作り込める。 |
| DDD | 業務知識、用語、ドメインモデル | DDDで得たモデルと境界を、仕様と設計の前提として使える。 |

SDDはBDD、TDD、DDDの代替ではない。仕様から実装までの縦方向の流れを管理し、その中で各手法を利用する。

## ウォーターフォールとの違い

| 観点 | 固定的な工程運用 | 反復的なSDD運用 |
| --- | --- | --- |
| 仕様 | 実装前に広い範囲を確定する | 小さな機能単位で、実装可能な程度まで具体化する |
| 変更 | 後工程から正式な変更手続きで戻す | 実装の発見を仕様・設計へ継続的に反映する |
| 成果物 | 工程ごとの引き渡し資料 | AI、人、テストが参照する継続的な作業成果物 |
| リリース | 大きな単位になりやすい | 独立して価値を確認できる小さな単位を目指す |

SDDでも規制や契約上の正式な承認ゲートを設けられる。違いは、仕様を実装後に使わない静的文書ではなく、開発中も更新・検証する中心成果物として扱う点にある。

## よくある失敗

| 失敗 | 問題 | 対応 |
| --- | --- | --- |
| 仕様をAIに一度で完成させる | もっともらしくても業務上正しいとは限らない | 対象範囲、例外、受入条件を人が確認する。 |
| 仕様を細かくしすぎる | 設計変更のたびに要求文書が壊れる | 要求は結果、設計は実現方法として分ける。 |
| 大きな仕様を一度に実装する | AIが途中の制約を見落としやすい | 独立してテストできる機能とタスクへ分ける。 |
| 仕様とコードの同期方法がない | 仕様が古い参考資料になる | PR、要求ID、受入テスト、整合性確認を使う。 |
| AIが作ったテストだけで判断する | 誤った解釈のテストとコードが同時にできる | 重要な受入条件を人または独立した観点で確認する。 |
| 仕様作成を価値検証の代わりにする | 詳細な仕様でも需要は証明できない | インタビュー、プロトタイプ、実験を別途行う。 |

## 小さく導入する方法

1. `specs/<feature>/`に`spec.md`、`plan.md`、`tasks.md`を置く。
2. `spec.md`へ目的、対象、対象外、要求、受入条件を書く。
3. 人が仕様をレビューし、未確定事項を解消する。
4. `plan.md`へ変更箇所、データ、API、テスト、リスクを書く。
5. `tasks.md`へ要求ID付きの小さなタスクを書く。
6. AIには1タスクずつ依頼し、テストと差分を確認する。
7. PRで仕様、設計、コード、テストの整合性を確認する。

定着してから、テンプレート生成、仕様チェック、タスク自動実行、承認ゲートを段階的に追加する。

## 最小テンプレート

```md
# <機能名>

## 背景・目的

## 利用者

## 対象範囲

### 対象

### 対象外

## 要求

- FR-001: <誰が、どの条件で、何をできること>

## 受入条件

- Given: <前提>
  When: <操作・契機>
  Then: <観測できる結果>

## 非機能条件

## 前提・依存・未確定事項

## 対応する設計・タスク・テスト
```

仕様の品質は文書量ではなく、実装範囲を決められるか、第三者が達成を判定できるか、変更の影響を追跡できるかで評価する。

## レビュー観点

- 解決する問題と利用者が明確か。
- 対象と対象外が書かれているか。
- 要求と実装方法が混在していないか。
- 要求が一意に読め、テスト可能か。
- 重要な正常系、例外、境界、権限が扱われているか。
- 成功指標と受入条件を区別しているか。
- 設計とタスクが要求へ追跡できるか。
- 各タスクに完了条件と検証方法があるか。
- プロジェクトの原則や既存設計に反していないか。
- AIによる仮定と、人が合意した決定を区別しているか。
- 仕様変更時の影響範囲が分かるか。
- 実装後も仕様、テスト、コードが一致しているか。
